# 阶段 02：PostgreSQL 关系设计说明

## 依据

沿用项目文件《需求文档.docx》第 6 章与图 6-1～图 6-5，以及推进方案第 6、7 章。
本文件记录本次**实际落地的关系设计**；不是已经完成的性能/并发测试结果。

## 业务关键关系

- `users` 1:N `orders`；`stores` 1:N `orders`；柜台单可通过 `employees` 归因。
- `stores` N:M `products`，由 `store_products` 持有门店售价与版本。
- `bundles` N:M `products`，由 `bundle_items` 定义套餐组成。
- `orders` 1:N `order_items`；`order_items` 1:N `order_item_components`，后者是创建订单时冻结的 SKU 消耗快照。
- `stores` × `products` 唯一对应一条 `inventory`；每一次扣库/补货/调整写 `inventory_ledger`。
- `orders` 0..1:1 `payments`；支付时库存、券、积分、支付、订单状态必须同事务提交。
- `users` 1:0..1 `member_accounts`，账户 1:N `points_ledger`；用户 1:N `user_coupons`。
- `price_recommendations` 只代表待审或已审建议；真正生效的历史保存在 `store_price_changes`。

## 实体和表

基础与组织：`users`、`stores`、`employees`

商品与库存：`products`、`store_products`、`bundles`、`bundle_items`、`inventory`、`inventory_ledger`

订单与支付：`orders`、`order_items`、`order_item_components`、`payments`、`idempotency_requests`

营销与会员：`coupon_templates`、`user_coupons`、`member_accounts`、`points_ledger`

审计与智能增强：`audit_logs`、`agent_runs`、`agent_tool_calls`、`price_recommendations`、`store_price_changes`

合计 **23 张业务表**，采用单个正式初始 Alembic 迁移创建。后端模块按开发阶段逐项接入。

## 约束与设计决策

1. 所有主键使用 PostgreSQL `bigint GENERATED BY DEFAULT AS IDENTITY`；核心引用使用外键。
2. 订单/商品价格使用整数分，订单快照不随今后改价改变。
3. `inventory.available_qty >= 0`，并使用唯一键 `(store_id, product_id)`。支付扣库必须执行条件更新，不能只做 Python 先读后改。
4. `member_accounts.points_balance >= 0`，积分流水记录 `balance_before`/`balance_after`。
5. `orders` 的 `order_source=ONLINE` 必须没有员工；`COUNTER` 必须有员工；员工是否属于对应门店由后端服务校验。
6. `orders.user_coupon_id` 与 `user_coupons.redeemed_order_id` 互相引用，用后置外键约束处理建表顺序。
7. 同一订单最多一条成功支付记录，由 `payments.order_id UNIQUE` 约束。
8. `idempotency_requests` 通过 `(actor_id, scope, request_key)` 唯一约束保证请求去重依据。
9. `store_products.price_version` 与 `bundles.price_version` 用于页面报价和后端版本校验。后者是为落实套餐价格版本校验增加的**实现字段**，不改变需求功能。
10. JSONB 仅用于审计、Agent 调用、推荐指标快照，不用于订单与库存核心业务字段。

## 统计口径

- 销售金额：`orders.status IN ('PAID','COMPLETED')` 下 `SUM(orders.payable_cents)`，以 `paid_at` 过滤。
- 订单数：使用相同筛选条件 `COUNT(DISTINCT orders.id)`。
- 商品/套餐作为订单行分别计量；套餐消耗的 SKU 从 `order_item_components` 分析，不能把套餐售价与其成分售价再相加。
- 柜台员工业绩按 `orders.employee_id`，线上订单不归因员工。
- 业务日按 `Asia/Shanghai` 解释，数据库时间使用 `timestamptz`。

## 留待阶段 03 编写的业务规则

仅靠数据库约束无法完整保证：订单状态迁移、价格版本并发校验、优惠券适用性、积分扣减与获取规则、跨店授权、支付幂等返回及支付原子事务。以上在 FastAPI 业务服务层落实并通过真实接口验收。

## 设计阶段尚需教师确认的需求文档事项

- 柜台员工销售归因口径：建议只归因 `COUNTER` 订单。
- 套餐销售口径：建议把套餐作为独立销售项，组成 SKU 只计算库存消耗。
- 性能阈值：需求文档里的 P95 为拟定值，非已实测结果。

## 本轮交付

注意：第一次创建数据库前需在项目根目录把 `.env.example` 复制成 `.env` 并设置自己使用的本地密码。已创建数据库卷时，修改 `.env` 密码不会自动修改数据库中已有用户密码。
